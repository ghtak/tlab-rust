# RBAC 구조와 권한 코드

RBAC는 사용자가 시스템에서 수행할 수 있는 작업을 판단한다. 퍼미션 코드는 `리소스:액션` 형식으로 정의한다. 예를 들어 `user:manage`는 사용자 관리 작업, `file:manage`는 파일 관리 작업을 뜻한다. URL마다 퍼미션을 만들거나 `*:*` 같은 전체 허용 코드를 두지 않는다. 역할은 업무상 필요한 퍼미션을 묶고, 사용자에게 역할을 할당한다.

## 테이블 구조

스키마는 [`004_create_rbac.sql`](../src/auth/migrations/004_create_rbac.sql)에 정의한다.

| 테이블 | 주요 컬럼 | 관계와 제약 |
| --- | --- | --- |
| `tlab_role` | `id`, `code`, `description` | `id` 기본 키, `code` 고유 |
| `tlab_permission` | `id`, `code`, `description` | `id` 기본 키, `code` 고유 |
| `tlab_role_permission` | `role_id`, `permission_id` | 역할과 퍼미션의 다대다 관계, 두 ID가 복합 기본 키 |
| `tlab_user_role` | `user_account_id`, `role_id` | 사용자와 역할의 다대다 관계, 두 ID가 복합 기본 키 |

연결 테이블의 ID는 각각 `tlab_user_account`, `tlab_role`, `tlab_permission`을 외래 키로 참조한다. 참조 대상이 삭제되면 연결 행도 삭제된다. `code`는 권한 검사에 사용하는 안정적인 식별자이며, 표시나 설명은 `description`에 둔다.

## 권한을 나누는 기준

- 역할 코드는 `admin`, `sales`처럼 업무상 책임을 나타낸다. 일반 로그인 사용자에게 기본 역할을 자동으로 부여할 필요는 없다.
- 퍼미션은 역할마다 허용 여부가 달라져야 하는 작업에 추가한다. API 경로 수나 CRUD 동사 수에 맞춰 미리 늘리지 않는다.
- `file:manage` 같은 퍼미션은 파일 관리 작업의 허용 여부를 나타낸다. 파일 소유자, 팀, 그룹, 공유 범위에 따른 접근 가능 여부는 파일 데이터를 조회하거나 변경할 때 별도로 판단한다.
- 목록·검색에서 접근 불가 파일을 제외하고, 상세 조회·다운로드에도 동일한 대상 조건을 적용한다.

## 리소스별 접근 규칙으로 확장

파일 소유자나 팀에 따라 접근 대상이 달라지면 RBAC 퍼미션을 파일별로 늘리지 않는다. 사용자 속성(계정 상태, 소속 팀·그룹)과 파일 속성(소유자, 공유 대상, 공개 범위)을 이용해 요청한 파일에 접근할 수 있는지 판단한다. 이 부분이 ABAC로 확장되는 범위다.

예를 들어 인증된 활성 사용자의 파일 읽기를 허용하더라도, 해당 파일의 소유자이거나 파일이 공유된 팀·그룹에 속하는지는 별도로 확인한다. 업로드한 파일을 수정·삭제할 수 있는 범위도 소유자 등의 조건으로 정한다. `file:manage`가 이런 대상 조건을 우회할 수 있는지 역시 관리 작업별 정책으로 명시한다. 역할을 가졌다는 이유만으로 모든 파일에 대한 접근을 자동 허용하지 않는다.

목록·검색·개수·내보내기는 접근 조건을 조회 쿼리에 적용하고, 파일 ID를 직접 받는 상세 조회·다운로드·수정·삭제에도 같은 조건을 적용한다. 팀·그룹 소속과 파일의 소유·공유 정보는 서버가 관리하는 현재 데이터를 사용한다. 구체적인 파일 및 소속 테이블은 파일 공유 요구사항이 정해질 때 설계한다.

## 현재 상태

`just migrate`는 스키마와 `admin`, `sales` 역할, `user:manage`, `file:manage` 퍼미션을 적용한다. 두 퍼미션은 `admin`에만 연결되며, `sales`에는 아직 퍼미션을 연결하지 않았다. 이어서 `just init-admin`을 실행하면 기본 관리자 계정 `admin@localhost`를 생성하고 `admin` 역할을 할당한다. 두 명령은 실행할 때마다 기본 역할·퍼미션 연결과 관리자 역할 할당을 다시 시도하므로, 이를 수동으로 해제해도 다음 실행에서 복원된다.

### HTTP 권한 검사

인증된 요청에서 `AccessClaims`가 액세스 토큰의 `role_ids`를 읽고, `auth/permission.rs`의 `require`가 `RbacService::has_permission`을 호출한다. 이 서비스는 해당 역할들의 퍼미션 코드를 DB에서 조회해 요청한 코드를 확인한다. 권한이 없으면 HTTP 403을 반환한다.

현재 사용자·역할·퍼미션 관리 API는 `user:manage`를 요구한다. 관련 라우트는 `auth/route.rs`, `auth/route/users.rs`, `auth/route/roles.rs`, `auth/route/permissions.rs`에 있다. `file:manage`는 기본 데이터에 등록되어 있지만 파일 API는 아직 없다.

액세스 토큰에는 발급 시점의 역할 ID가 들어간다. 역할에 연결된 퍼미션 변경은 DB 조회에 반영되지만, 사용자의 역할 변경은 기존 액세스 토큰에 즉시 반영되지 않을 수 있다. 새 액세스 토큰을 발급할 때 역할 ID를 다시 읽는다.

### 역할·퍼미션 관리

관리 API에서 역할과 퍼미션을 생성·조회·삭제하고, 사용자에게 역할을, 역할에 퍼미션을 배정할 수 있다. 연결 변경은 `SetUserRolesUsecase`와 `SetRolePermissionsUsecase`가 트랜잭션 안에서 전체 목록을 교체한다. 초기 관리자 `admin@localhost`의 `admin` 역할과 `admin` 역할의 `user:manage` 퍼미션은 제거할 수 없다. `admin` 역할 자체도 삭제할 수 없다.

새 기능에 RBAC를 적용할 때는 해당 작업의 퍼미션 코드를 정하고 `tlab_permission` 및 필요한 역할 연결을 등록한 뒤, 요청 처리 위치에서 `permission::require`를 호출한다. 권한 코드만으로 파일 소유권이나 공유 범위를 판단하지 않는다. 위의 리소스별 접근 규칙은 파일 기능을 구현할 때 별도로 적용한다.
