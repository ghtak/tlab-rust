# UI 메뉴 표시와 화면 접근 권한

로그인한 사용자의 권한 코드는 `GET /api/v1/auth/me` 응답의 `permissions` 배열에서 가져온다. UI의 메뉴 표시와 화면 진입은 이 코드를 기준으로 판단한다.

## 현재 화면 규칙

| 화면 | URL | 필요한 권한 |
| --- | --- | --- |
| 대시보드 | `/` | 로그인 |
| 퍼미션 관리 | `/permissions` | `access:manage` |
| 롤 관리와 롤별 퍼미션 | `/roles`, `/roles/:roleId/permissions` | `access:manage` |
| 사용자 관리와 사용자별 롤 | `/users`, `/users/:userId/roles` | `access:manage` |

권한이 없는 메뉴와 대시보드 바로가기는 표시하지 않는다. 접근 관리 그룹은 표시할 자식 메뉴가 없으면 숨긴다. 주소를 직접 입력한 경우에도 라우트의 `beforeLoad`가 권한을 검사하며, 부족하면 접근 불가 화면을 보여준다. 로그인하지 않은 사용자는 기존과 같이 로그인 화면으로 이동한다.

## 새 화면을 추가할 때

1. 서버 API에서 해당 작업에 필요한 권한 코드를 정한다. 메뉴만을 위한 권한 코드는 만들지 않는다.
2. `src/features/auth/access.ts`의 `pageAccess`에 화면의 요구 권한을 정의한다.
3. 라우트의 `beforeLoad`에서 `requirePermission(context.user, pageAccess.<화면>)`을 호출한다. 같은 권한을 쓰는 하위 화면은 부모 라우트에서 검사한다.
4. 사이드메뉴 항목과 대시보드 바로가기에 같은 `pageAccess` 값을 연결한다. 표시는 `hasPermission`으로 판단한다.
5. 권한이 있는 사용자와 없는 사용자의 메뉴, 바로가기, 직접 URL 접근을 확인한다.

## 권한 변경과 API 응답

롤의 퍼미션 또는 사용자의 롤을 저장하면 UI는 `currentUser` 조회와 라우트를 갱신한다. 다른 세션에서 권한이 변경되면 화면 갱신 전까지 표시가 이전 상태일 수 있다. 실제 데이터 접근은 서버 API의 권한 검사가 결정하며, UI의 표시 및 라우트 검사는 이를 대신하지 않는다.

`/auth/me`는 현재 DB의 권한을 반환하고 API 권한 검사는 토큰의 역할 ID를 사용한다. 사용자 롤 변경 직후 기존 토큰의 역할 정보와 `/auth/me` 결과가 달라질 수 있다. 즉시 일치를 요구하는 경우에는 서버의 토큰 갱신 정책도 함께 검토해야 한다.
